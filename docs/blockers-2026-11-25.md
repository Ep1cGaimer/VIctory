# Problems and blockers: VIctory world at 30 fps on an NVIDIA laptop (2026-11-25)

Written for a reviewer who has not seen the session. Branch `victory-world-30fps-v2` on Ep1cGaimer/VIctory (head after this doc); details and history in `docs/handoff-victory-world-30fps.md`.

## Setup and rules
- Machine: RTX 4060 Laptop 8 GB (7,956 MB), 15.3 GB RAM, Ryzen 7 7840HS (AMD 780M iGPU also present; check the "host adapter" log line). Windows 11.
- Game: GTA6 Xbox Series X build at `C:\Games\GTA6.Xbox.v1.0.2.1-CYBERLEEK`. **Never write to the game folder**; fingerprint after each run must stay `109 224001114630 2026-11-24T09:04:57.8026955Z` (it did, every run).
- Code from other repos and forks is fine once it is reviewed first, **except code from unmerged pull requests** (open, or closed without merging). Mind licences (VIctory is GPL-3.0-or-later; XCL is GPL-2.0, so ideas only from it). Don't run other repos' shipped scripts or binaries; building their source after review is OK.
- Runs: `labRoot/run-probe.ps1` (labRoot = `%TEMP%/victory-30fps-lab`), keys injected with `VICTORY_KEYS`; a run takes the machine 5–10 min.

## Blockers, most important first

### 1. NVIDIA has no 64-lane waves: ~104 compute pipelines still refused
- The title's compute programs mostly run as wave64. D3D12 on NVIDIA reports 32..32. Our census: 132 refused non-builder programs (8 need no cross-lane work, 38 only shared LDS, 86 cross halves: 62 `v_mbcnt`, 24 `v_readlane`/`v_writelane`).
- Their outputs are never written, so readers loop on garbage counts: wind `00167d58cc5a78d7` (`WindNew:CS_CopyLatestWindFieldForRenderingWithSmooth`) 1,126 ms average, up to 2.7 s; `8bbcbda6008eaa37` 388 ms. Skipping wind alone: 1,740 → 874 ms.
- Ported from ztrx `main` (opt-in `VICTORY_WAVE_HALVES=1`): tiers 1–2 (wave32 directly; LDS with a barrier before each access, `lds_meetings`, `wave_base` counter). Enables 28 more pipelines. **Tier 3 (cross-half exchange for `v_mbcnt`, `readlane`, masks as numbers) is not ported.** Still refused: wind `FeedbackToParent4x4x4`, scattering `SortRayTiles`, `CloudMultiScatteringCache`, `GatherDiffusion`, `GatherDensityAreaForReadBack`, `SkyRadianceCache_Camera_Gather`, `DensityShadowMapMips`.
- Belobug has a "console flow" lowering (exchange in groupshared memory, `structure_console`), but its `translate --host-lanes 32-32` still fails 167 "console wave64 lanes" and 128 "wave64 group sharing LDS" (all variants in shaders.rpf). Its lower.rs history includes "Merge PR #193/#176/#160/#164 … into the integration": upstream PRs that were closed without merging (#160, #164, #176, #193; checked 2026-11-25), so code that came from those PRs can't be used. Whether the console-flow code itself is Belobug's own work or from such a PR is not traced yet; if it is its own, it can be used after review.
- Question: is a general tier-3 exchange the right path, or is there a cheaper route (e.g. writing the missing producers' outputs with defaults so readers' loops terminate, or bounding the specific loops)?

### 2. With `VICTORY_WAVE_HALVES=1` the title stalls at the account picker
- 13 draws a frame for 10 minutes. Skipping all 28 newly enabled pipelines (`VICTORY_SKIP_PIPELINES`) lets it reach the world at 212 s.
- Of the 28, **24 are the LDS class** (`split_lds`/`lds_meetings`) that Belobug refuses on NVIDIA and still passes the picker; 4 are tier 1. Next step: one run skipping only those 24, then bisect them (~5 runs of 270 s).
- An earlier run on the AMD iGPU (native wave64) stalled the same way, while Belobug on an RX 9070 runs everything natively and gets in. So the trigger may be a CPU-side bug that only bites once these producers write data (Belobug's page-guard / copy-back fixes, e.g. `18e3849`), not the lowering itself.
- An earlier bisect was cut short; one step was spoiled by a key press in the window; a later restart was denied by the auto-mode permission check.

### 3. GPU time per frame even without runaway loops
- 432 ms median at loop limit 256, still ~13x over 33 ms.
- Indirect draws: before each one we run a clamp dispatch plus three barriers, ~9,300 a frame in the world. Belobug records them in a list ahead of each run (`ccab973`, `918ab03`, `76387c2`; its own `main` commits, so allowed): 225 → 72–80 ms on its card. **Its patch does not apply** (≈400 lines across `draw.rs`, `host.rs`, `list.rs`, `indirect.rs` diverged); needs a hand port, plus its mode-7 fix (clamps serialized) against mesh flicker.
- Ray-tracing structure builder gated off by default (it wrote garbage with some stages refused), so no RT lighting; Belobug substitutes a constant ambient (`VICTORY_AMBIENT`).

### 4. CPU time per frame
- 0.3–6 s "preparing": copies of title memory (200–400 MB a frame), texture uploads, bindless plans/records. Not yet profiled to a fix. Belobug's dirty-span merge in `copy_back` (`18e3849`) is a candidate idea.

### 5. Memory
- 8 GB VRAM + 15.3 GB RAM vs the console's 16 GB shared. The emulator keeps title memory plus host copies, so effectively less than the console. We commit 20+ GB and grow; Belobug (built for 16 GB VRAM / 64 GB RAM, 22–33 GB) runs out of video memory here.

### 6. Translation gaps shared with upstream
- 195 programs: "an address in an SGPR that is no root parameter" (e.g. `GS_VoxelizeGeneric`).
- 71 mesh shaders: outputs beyond the host's 32 KiB.
- Draws dropped "a table not made" for some indirect kinds.

### 7. Tooling and process
- Each game run takes 5–10 min and the whole machine; the owner must not touch the window (`VICTORY_KEYS` drives input).
- Auto-mode permission check denied restarting the bisect; needs explicit owner OK each time.
- The "first frame with >100 draws" progress metric also fires on intro and menus; a real "in the world" detector is needed (e.g. a draw-count threshold over several seconds, or a captured-frame check).
- Shader-cache warm-up: `victory translate --cache --jobs 8` (ours) takes ~3–4 min; Belobug has no `--cache`, so its first run is cold (hundreds of pipelines "being made").

## Questions for the reviewer
1. Fastest path to remove the runaway loops on NVIDIA: tier-3 lowering, or a targeted workaround?
2. How to find the account-picker stall without many 5-minute runs (offline replay? log which new pipeline writes which title buffer?)
3. Is 30 fps with full graphics realistic on 8 GB VRAM / 15.3 GB RAM at all, and if not, what target should we set (e.g. stable 30 fps at reduced settings)?
4. Order of work: hoisted clamps vs CPU copies vs memory.
